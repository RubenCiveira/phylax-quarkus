# Análisis de diseño y plan de refactor — Forms OIDC (Java)

> Documento paralelo a `ANALISIS_SIMPLIFICACION_FORMS_OIDC.md` (PHP).
> Adapta sus conclusiones al stack Java/Quarkus de phylax-api.

---

## 1. Inventario de problemas del diseño actual

### 1.1 No existe interfaz común para los ControllerParts

Todos los parts son clases concretas sin interfaz compartida. El método `process()` tiene
firmas **distintas** entre parts:

```java
// MfaControllerPart — tiene parámetro extra List<AuthenticationChallege>
Optional<Response> process(String step, Optional<String> oUser, ClientDetails clientDetails,
    AuthRequest request, MultivaluedMap<String, String> paramMap,
    Function<StepResult, Response> resolver, List<AuthenticationChallege> challenges)

// ConsentControllerPart, NewPassControllerPart, ScopeConsentControllerPart, etc.
Optional<Response> process(String step, Optional<String> oUser, ClientDetails clientDetails,
    AuthRequest request, MultivaluedMap<String, String> paramMap,
    Function<StepResult, Response> resolver)
```

Consecuencias:
- `FrontAcessController.doExecStep()` llama a cada part explícitamente (8 llamadas
  `fillIfEmpty` hardcodeadas + 5 ramas `else if` para steps especiales).
- Añadir un nuevo step requiere editar `FrontAcessController`.
- No es posible inyectar los parts como `List<InterfazComún>` ni aplicar ningún patrón
  de registro dinámico.

### 1.2 Estado mutable en FrontAcessController

```java
private MultivaluedMap<String, String> formParams;   // línea 220
private Challenge currentChallenge;                  // línea 224
```

Ambos son campos de instancia en un bean `@RequestScoped`.
- `formParams` se asigna en `doExecStep()` y se lee en `redirect()`. Si `redirect()` se
  invoca desde otro camino de código sin pasar por `doExecStep()`, el campo puede ser
  `null` o contener datos de otra rama.
- `currentChallenge` se actualiza como efecto lateral dentro de
  `preSessionUsername()`. Cualquier ruta que llame a `revolve()` sin haber pasado antes
  por `preSessionUsername()` puede leer un estado inconsistente.

### 1.3 Acoplamiento duro de ControllerParts a FrontAcessController

Todos los parts importan:
```java
import net.civeira.phylax.features.oauth.authentication.infrastructure.driver.html.FrontAcessController;
import net.civeira.phylax.features.oauth.authentication.infrastructure.driver.html.FrontAcessController.StepResult;
```

`StepResult` y `StartFormFlow` son inner classes de `FrontAcessController`. Los parts
dependen del controlador, cuando debería ser al revés.

### 1.4 Separación incompleta entre "pintar" y "procesar"

El método de entrada para renderizar un formulario cuando se produce un challenge
(`MfaRequiredException`, `ConsentRequiredException`, etc.) está cableado en
`FrontAcessController.map()`:

```java
loginErrorMappers.put(MfaRequiredException.class,
    FlowInfo.builder().chageller(mfaController.getChallenge())
        .function(mfa -> mfaController.doPaintMfaForm(mfa.getLocale(), mfa.getSession()))
        .build());
```

La lógica de qué challenge corresponde a qué part (`getChallenge()`) está en el part,
pero la conexión entre la excepción y la función de render está en el controlador. Si
añades un nuevo step debes tocar tres sitios: el part, `map()` y `doExecStep()`.

### 1.5 Construcción de URLs duplicada

`RecoverControllerPart` y `RegistrationControllerPart` tienen métodos privados idénticos:
```java
private String issuer(String tenant) {
    return current.getPublicHost() + "/oauth/openid/" + tenant;
}
```
Y construyen las URLs de callback con concatenaciones manuales + `URLEncoder`.
Cualquier cambio en la estructura de URLs exige editar múltiples clases.

### 1.6 Strings de error hardcodeados en español

| Fichero | Línea | Texto hardcodeado |
|---|---|---|
| `MfaControllerPart` | `doExecMfa()` | `"MFA incorrecto"` |
| `NewPassControllerPart` | `doExecNewPass()` | `"No se ha podido guardar"` |
| `RecoverControllerPart` | `doExecSendeRecover()` | `"No se ha podido guardar"` |
| `FrontAcessController` | `doExecLogin()` | `"Credenciales incorrectas"` |
| `FrontAcessController` | `revolve()` | `"Credenciales incorrectas"` |

El sistema i18n ya existe (`FrontAcessController.i18n()`). Solo falta usarlo.

### 1.7 FrontAcessController tiene 1121 líneas y está marcado @autogenerated

El fichero es el hub de todo el flujo OAuth y tiene una complejidad ciclomática muy alta.
Al estar marcado como `/* @autogenerated */` nadie sabe si debe editarse directamente,
lo que paraliza el desarrollo de nuevas features.

La misma marca aparece en **todos** los ControllerParts. Esto es una fuente de confusión
importante sobre la propiedad y el ciclo de vida del código.

### 1.8 map() con @Synchronized innecesario

```java
@Synchronized
private Map<Class<? extends AuthenticationException>, FlowInfo> map() {
    if (loginErrorMappers.isEmpty()) { ... }
    return loginErrorMappers;
}
```

El bean es `@RequestScoped` — se crea y destruye en cada petición. La inicialización
lazy con `@Synchronized` no aporta nada (el mapa siempre empieza vacío) y añade
confusión.

### 1.9 resolver como Function callback

Los parts reciben `Function<StepResult, Response> resolver` (que es siempre
`this::revolve` desde `FrontAcessController`). Esto crea un callback circular: el part
llama de vuelta al controlador. Un modelo de retorno tipado (`StepOutcome`) elimina
esta dependencia.

**Ubicación:** `features/oauth/authentication/domain/OidcFlowContext.java`

### 2.2 StepInput

Agrupa todos los datos que un step puede necesitar para pintar o procesar un formulario.
Reemplaza los parámetros sueltos de `process()`.

**Ubicación:** `features/oauth/authentication/infrastructure/driver/html/StepInput.java`
(capa de infraestructura, no de dominio, porque contiene `MultivaluedMap` de JAX-RS)

```java
@Value
@Builder
public class StepInput {
    OidcFlowContext context;
    ClientDetails clientDetails;
    Optional<ChallengesState> challenges;      // estado de pre-sesión (renombrado de Challenge)
    MultivaluedMap<String, String> formParams;

    // Helpers de conveniencia
    public Optional<String> currentUser() {
        return challenges.map(ChallengesState::getUsername);
    }

    public String step() {
        return formParams.getFirst("step") != null ? formParams.getFirst("step") : "";
    }

    public Locale locale() {
        return context.getLocale();
    }

    public String tenant() {
        return context.getTenant();
    }

    public AuthRequest toAuthRequest() {
        return context.toAuthRequest();
    }
}
```

### 2.3 StepOutcome

Resultado tipado de un step. Reemplaza el callback `Function<StepResult, Response>`.
Al devolver `Proceed`, el **llamador** (OidcStepRouter / FrontAcessController) es
responsable de continuar el flujo, no el step.

**Ubicación:** `features/oauth/authentication/infrastructure/driver/html/StepOutcome.java`

```java
public sealed interface StepOutcome permits StepOutcome.Render, StepOutcome.Proceed {

    /** El step quiere renderizar una respuesta HTML. */
    record Render(Response response) implements StepOutcome {}

    /** El step completó exitosamente y el flujo puede continuar. */
    record Proceed(String username, ClientDetails clientDetails, AuthRequest request)
            implements StepOutcome {}
}
```

`StepResult` (la inner class actual de `FrontAcessController`) se migra a `StepOutcome.Proceed`.

### 2.4 OidcStep (interfaz)

Contrato único para todos los steps del flujo OIDC. Unifica "pintar" y "procesar".

**Ubicación:** `features/oauth/authentication/infrastructure/driver/html/OidcStep.java`

```java
public interface OidcStep {

    /**
     * Challenge de autenticación que este step satisface.
     * Null si el step no corresponde a ningún challenge (ej: recover, register).
     */
    AuthenticationChallege challenge();

    /**
     * Nombres de "step" del formulario que este step puede manejar
     * tanto para render como para proceso.
     * Ej: RecoverStep retorna {"show-recover", "send-recover"}.
     */
    Set<String> stepNames();

    /**
     * Renderiza el formulario inicial de este step.
     * Llamado cuando se produce un challenge de autenticación,
     * o cuando step=show-xxx.
     *
     * @param input contexto de la petición
     * @param preSession cookie de pre-sesión a adjuntar a la respuesta
     */
    Response paint(StepInput input, NewCookie preSession);

    /**
     * Procesa un formulario enviado.
     * Retorna empty si el step no aplica al step actual.
     * Retorna Render si hay un error y hay que mostrar el formulario de nuevo.
     * Retorna Proceed si el step completó con éxito.
     *
     * @param input contexto de la petición
     */
    Optional<StepOutcome> process(StepInput input);
}
```

**Notas sobre migración de la lista de parámetros:**

| Parámetro actual | Origen en StepInput |
|---|---|
| `String step` | `input.step()` |
| `Optional<String> oUser` | `input.currentUser()` |
| `ClientDetails clientDetails` | `input.getClientDetails()` |
| `AuthRequest request` | `input.toAuthRequest()` |
| `MultivaluedMap<String, String> paramMap` | `input.getFormParams()` |
| `Locale locale` | `input.locale()` |
| `List<AuthenticationChallege> challenges` | `input.getChallenges()...` |

### 2.5 OidcStepRouter

Responsable de:
1. Encontrar el step que maneja el step actual (proceso).
2. Encontrar el step que renderiza un challenge (pintar).

Reemplaza la cadena de `fillIfEmpty` y el mapa `loginErrorMappers`.

**Ubicación:** `features/oauth/authentication/infrastructure/driver/html/OidcStepRouter.java`

```java
@ApplicationScoped
public class OidcStepRouter {

    // CDI inyecta todas las implementaciones de OidcStep
    @Inject @Any
    Instance<OidcStep> allSteps;

    // Cache inicializado al primer uso
    private volatile Map<String, OidcStep> byStepName;
    private volatile Map<AuthenticationChallege, OidcStep> byChallenge;

    /** Procesa un formulario enviado. Retorna empty si ningún step lo maneja. */
    public Optional<StepOutcome> process(StepInput input) {
        initCache();
        OidcStep step = byStepName.get(input.step());
        return step != null ? step.process(input) : Optional.empty();
    }

    /** Renderiza el formulario correspondiente a un challenge. */
    public Optional<Response> paint(AuthenticationChallege challenge,
                                    StepInput input, NewCookie preSession) {
        initCache();
        OidcStep step = byChallenge.get(challenge);
        return step != null ? Optional.of(step.paint(input, preSession)) : Optional.empty();
    }

    /** Retorna el OidcStep para un challenge dado (para obtener getChallenge()). */
    public Optional<OidcStep> stepForChallenge(AuthenticationChallege challenge) {
        initCache();
        return Optional.ofNullable(byChallenge.get(challenge));
    }

    private synchronized void initCache() {
        if (byStepName != null) return;
        byStepName = new HashMap<>();
        byChallenge = new HashMap<>();
        allSteps.forEach(step -> {
            step.stepNames().forEach(name -> byStepName.put(name, step));
            if (step.challenge() != null) {
                byChallenge.put(step.challenge(), step);
            }
        });
    }
}
```

**Nota CDI/Quarkus:** Los beans `OidcStep` deben ser `@ApplicationScoped` (o `@Dependent`)
para poder ser inyectados en un `@ApplicationScoped` router. En el nuevo diseño, los
steps no guardan estado por petición — todo viaja en `StepInput`.

### 2.6 OidcUrlBuilder

Centraliza la construcción de URLs de callback, eliminando la duplicación entre
`RecoverControllerPart` y `RegistrationControllerPart`.

**Ubicación:** `features/oauth/authentication/infrastructure/driver/html/OidcUrlBuilder.java`

```java
@ApplicationScoped
@RequiredArgsConstructor
public class OidcUrlBuilder {

    private final CurrentRequest current;

    public String issuer(String tenant) {
        return current.getPublicHost() + "/oauth/openid/" + tenant;
    }

    public String recoverCallbackUrl(StepInput input, String username) {
        ClientDetails client = input.getClientDetails();
        AuthRequest request = input.toAuthRequest();
        return issuer(input.tenant()) + "/recover"
            + "?username=" + encode(username)
            + "&client_id=" + encode(client.getClientId())
            + request.encodeInUrl()
            + "&recovercode=";
    }

    public String registerCallbackUrl(StepInput input, String email) {
        ClientDetails client = input.getClientDetails();
        AuthRequest request = input.toAuthRequest();
        return issuer(input.tenant()) + "/register"
            + "?email=" + encode(email)
            + "&client_id=" + encode(client.getClientId())
            + request.encodeInUrl()
            + "&regcode=";
    }

    private static String encode(String s) {
        return URLEncoder.encode(s, StandardCharsets.UTF_8);
    }
}
```

### 2.7 ChallengesState

Renombrar y limpiar la inner class `FrontAcessController.Challenge`.
Actualmente es mutable (`@Data`) y vive dentro del controlador.
Moverla a su propio fichero, hacerla inmutable.

**Ubicación:** `features/oauth/authentication/domain/ChallengesState.java`

```java
@Value
@Builder
@RegisterForReflection
public class ChallengesState {
    String username;

    @Builder.Default
    List<AuthenticationChallenge> challenges = List.of();

    // Permite extender sin cambiar la firma serializada
    @Builder.Default
    Map<String, String> extra = Map.of();

    public ChallengesState withChallenge(AuthenticationChallege additional) {
        List<AuthenticationChallenge> next = new ArrayList<>(challenges);
        next.add(additional);
        return toBuilder().challenges(Collections.unmodifiableList(next)).build();
    }
}
```

### 2.8 FrontAcessController simplificado

Con el nuevo diseño, `FrontAcessController` reduce su responsabilidad a:

1. Parsear los parámetros JAX-RS y construir `OidcFlowContext`.
2. Validar el cliente OAuth.
3. Gestionar cookies de sesión/pre-sesión.
4. Delegar a `OidcStepRouter`.
5. Manejar el resultado (`StepOutcome.Render` o `StepOutcome.Proceed`).

```java
// Pseudocódigo del nuevo processForm
@POST @Path("/oauth/openid/{tenant}/auth")
public Response processForm(...) {
    OidcFlowContext context = OidcFlowContext.from(tenant, clientId, ...);
    ClientDetails client = loadClient(context).orElse/* redirect error */;

    ChallengesState challengeState = loadPreSession(context.getPreSessionId(), tenant);
    StepInput input = StepInput.builder()
        .context(context)
        .clientDetails(client)
        .challenges(Optional.ofNullable(challengeState))
        .formParams(paramMap)
        .build();

    // Intenta delegar a un step especializado
    Optional<StepOutcome> outcome = router.process(input);

    if (outcome.isPresent()) {
        return handleOutcome(outcome.get(), input);
    }

    // Sin step coincidente: ejecutar login con usuario/contraseña
    return doExecLogin(input);
}

private Response handleOutcome(StepOutcome outcome, StepInput input) {
    return switch (outcome) {
        case StepOutcome.Render r -> r.response();
        case StepOutcome.Proceed p -> revolve(p.username(), p.clientDetails(), p.request());
    };
}
```

**Resultado esperado:** `FrontAcessController` pasa de 1121 líneas a ~350, con lógica
puramente orquestadora sin conocimiento de los pasos concretos.

## 3. Ejemplo: migración de MfaControllerPart a MfaStep

### Antes (actual)

```java
@RequestScoped
public class MfaControllerPart {
    public Optional<Response> process(String step, Optional<String> oUser,
            ClientDetails clientDetails, AuthRequest request,
            MultivaluedMap<String, String> paramMap,
            Function<StepResult, Response> resolver,
            List<AuthenticationChallege> challenges) {
        if ("mfa".equals(step) && oUser.isPresent()) {
            return Optional.of(doExecMfa(clientDetails, request, paramMap,
                oUser.get(), resolver, challenges));
        }
        return Optional.empty();
    }

    private Response doExecMfa(...) {
        boolean valid = userMfa.verifyOtp(...);
        if (valid) {
            return resolver.apply(StepResult.builder()...build()); // callback
        } else {
            return securer.secureHtmlResponse(doPaintMfaFormContent(locale, "MFA incorrecto"));
        }
    }
}
```

### Después (nuevo)

```java
@ApplicationScoped
@RequiredArgsConstructor
public class MfaStep implements OidcStep {

    private final SecureHtmlBuilder securer;
    private final UserMfa userMfa;
    private final DecoratePageGateway decorator;

    @Override
    public AuthenticationChallege challenge() {
        return AuthenticationChallege.MFA;
    }

    @Override
    public Set<String> stepNames() {
        return Set.of("mfa");
    }

    @Override
    public Response paint(StepInput input, NewCookie preSession) {
        return securer.secureHtmlResponse(buildForm(input.locale(), null).cookie(preSession));
    }

    @Override
    public Optional<StepOutcome> process(StepInput input) {
        if (!"mfa".equals(input.step()) || input.currentUser().isEmpty()) {
            return Optional.empty();
        }
        String username = input.currentUser().get();
        String code = input.getFormParams().getFirst("mfa_code");
        boolean valid = userMfa.verifyOtp(input.tenant(), username, code);
        if (valid) {
            return Optional.of(new StepOutcome.Proceed(
                username, input.getClientDetails(), input.toAuthRequest()));
        } else {
            String msg = i18n(input.locale(), "mfa.wrong-code");
            return Optional.of(new StepOutcome.Render(
                securer.secureHtmlResponse(buildForm(input.locale(), msg))));
        }
    }

    private ResponseBuilder buildForm(Locale locale, String msg) { ... }
}
```

**Diferencias clave:**
- `@ApplicationScoped` en lugar de `@RequestScoped` (sin estado por petición).
- Sin `Function<StepResult, Response> resolver` — devuelve `StepOutcome`.
- Sin importaciones de `FrontAcessController`.
- Error i18n en lugar de string hardcodeado.
- `stepNames()` declara qué steps maneja.

## 4. Plan de migración

La migración debe ser incremental para no romper el flujo existente. Cada fase es
deployable de forma independiente.

### Fase 1 — Crear estructuras de datos nuevas (sin modificar el flujo)

**Objetivo:** Introducir `OidcFlowContext`, `StepInput`, `StepOutcome` y `ChallengesState`
sin tocar `FrontAcessController` ni los ControllerParts.

**Tareas:**
1. Crear `OidcFlowContext` con su factory `from(...)`.
2. Crear `StepInput` con sus helpers de conveniencia.
3. Crear `StepOutcome` como interfaz sellada (`Render` + `Proceed`).
4. Crear `ChallengesState` (copia de `Challenge`, sin inner class).
5. Eliminar marca `/* @autogenerated */` de todos los ficheros de `part/` y de
   `FrontAcessController` — tomar propiedad del código.

**Criterio de fin:** Todos los nuevos tipos compilan. El flujo existente no cambia.

---

### Fase 2 — Definir OidcStep y crear OidcStepRouter vacío

**Objetivo:** Crear la interfaz y el router, pero sin conectarlos aún al controlador.

**Tareas:**
1. Crear interfaz `OidcStep` con `challenge()`, `stepNames()`, `paint()`, `process()`.
2. Crear `OidcStepRouter` que inyecta `Instance<OidcStep>`.
3. Crear `OidcUrlBuilder` y mover `issuer()` de RecoverControllerPart y
   RegistrationControllerPart al builder.
4. Mover `StepResult` fuera de `FrontAcessController` → renombrar a `StepOutcome.Proceed`
   o mantener como clase de compatibilidad que extiende el nuevo tipo.

**Criterio de fin:** Router y builder compilan e inyectan sin errores. Aún no se usan.

---

### Fase 3 — Migrar ControllerParts a OidcStep (uno por uno)

**Objetivo:** Convertir cada ControllerPart en una implementación de `OidcStep`.

**Orden recomendado (de menor a mayor complejidad):**

| Step | Motivo del orden |
|---|---|
| `MfaStep` | Más sencillo, sin URLs ni pasos secundarios |
| `ScopeConsentStep` | Simple, un único step name |
| `ConsentStep` | Parecido, más lógica de negocio |
| `NewPassStep` | Cifrado de campos pero flujo lineal |
| `NewMfaStep` | Similar a Mfa |
| `DelegatedStep` | Tiene steps "show" y "process" distintos |
| `RecoverStep` | Usa OidcUrlBuilder, flujo en dos fases |
| `RegistrationStep` | Más complejo, múltiples estados (OK, PENDING, CANCEL) |

**Para cada migración:**
1. Crear `XxxStep implements OidcStep` con `@ApplicationScoped`.
2. Mover lógica de `doPaint*` → `paint()`.
3. Mover lógica de `process()` → `process()`, sustituyendo `resolver.apply(...)` por
   `return Optional.of(new StepOutcome.Proceed(...))`.
4. Declarar `stepNames()` con todos los step names que manejaba la parte (incluyendo
   los "show-xxx" que antes estaban en el `else if` de `doExecStep()`).
5. Reemplazar strings hardcodeados con `i18n(input.locale(), "key")`.
6. Eliminar la clase `XxxControllerPart` original una vez validado.

**Criterio de fin para cada step:** El paso funciona vía `OidcStepRouter` sin pasar por
la cadena `fillIfEmpty`.

---

### Fase 4 — Conectar OidcStepRouter en FrontAcessController

**Objetivo:** Sustituir la cadena `fillIfEmpty` + `else if` de `doExecStep()` por
una llamada al router.

**Tareas:**
1. Inyectar `OidcStepRouter` en `FrontAcessController`.
2. Reemplazar el bloque `fillIfEmpty` + `else if` por:
   ```java
   Optional<StepOutcome> outcome = router.process(input);
   ```
3. Reemplazar `loginErrorMappers` (`map()`) por llamadas a `router.paint(challenge, input, preSession)`.
4. Convertir `formParams` y `currentChallenge` de campos de instancia a variables locales
   en los métodos que los necesitan.
5. Extraer la construcción de `OidcFlowContext` a un método `buildContext(...)`.

**Criterio de fin:** `doExecStep()` tiene menos de 20 líneas.

---

### Fase 5 — Simplificar FrontAcessController

**Objetivo:** Dejar el controlador como puro orquestador de sesión y redirecciones.

**Tareas:**
1. Extraer la lógica de cookies a un helper `OidcCookieManager` (equivalente PHP).
2. Extraer la construcción de `TemporalAuthCode` + redirect URL a un helper de respuesta.
3. El método `revolve()` pasa a ser `handleProceed(StepOutcome.Proceed)`.
4. Eliminar los inner classes `FlowInfo` y `StartFormFlow` (ya no son necesarios).
5. Eliminar `map()` y `loginErrorMappers`.

**Criterio de fin:** `FrontAcessController` tiene ≤400 líneas sin lógica de rendering.

---

### Fase 6 — Migrar Challenge a ChallengesState

**Objetivo:** Eliminar la clase mutable `Challenge` y usar `ChallengesState` inmutable.

**Tareas:**
1. Reemplazar usos de `Challenge` por `ChallengesState` en todo el código migrado.
2. Actualizar serialización JWT (`buildChallengerToken` / `verifyChalleger`) para
   usar `ChallengesState`.
3. Añadir campo `extra: Map<String, String>` para extensibilidad futura.
4. Mantener compatibilidad de deserialización hacia atrás (gestionar cookies existentes
   en producción durante el despliegue).

**Criterio de fin:** No hay referencias a `FrontAcessController.Challenge`.

## 5. Consideraciones Java/Quarkus específicas

### 5.1 Scope de los OidcStep beans

Los ControllerParts actuales son `@RequestScoped`. En el nuevo diseño, los `OidcStep`
no guardan estado por petición (todo llega vía `StepInput`), por lo que pueden ser
`@ApplicationScoped`. Esto mejora el rendimiento y simplifica el ciclo de vida.

Si algún step necesita acceder a beans `@RequestScoped` (como `CurrentRequest`),
puede inyectarlos directamente — CDI gestiona la resolución via proxy.

### 5.2 Inyección de Instance<OidcStep>

```java
@Inject @Any
Instance<OidcStep> allSteps;
```

Quarkus soporta `Instance<T>` con `@Any` en `@ApplicationScoped`. Todos los beans
que implementen `OidcStep` serán descubiertos automáticamente.

**Atención:** Quarkus Panache y CDI necesitan que las clases sean `public` y no `final`
para generar proxies. Los `OidcStep` deben seguir esta regla.

### 5.3 Sealed interfaces y pattern matching (Java 21)

El `StepOutcome` sellado permite usar `switch` con pattern matching:
```java
return switch (outcome) {
    case StepOutcome.Render r -> r.response();
    case StepOutcome.Proceed p -> revolve(p);
};
```
Quarkus 3.x soporta Java 21.

### 5.4 @RegisterForReflection en ChallengesState

`ChallengesState` se serializa en JWT via Jackson. Requiere:
```java
@RegisterForReflection
```
para que funcione en modo nativo (GraalVM).

### 5.5 Orden de migración y tests

Los tests de integración existentes (`OidcIntegrationTestBase`) deben ejecutarse después
de cada fase. El grupo `oidc-flow` valida los flujos completos:
```bash
mvn test -Dgroups="oidc-flow"
```

## 6. Riesgos y mitigaciones

| Riesgo | Mitigación |
|---|---|
| Cookies `PRE_SESSION_ID` existentes con formato `Challenge` en producción durante migración | En Fase 6, mantener deserializador legado que acepta tanto `Challenge` como `ChallengesState` |
| Orden de steps no determinista con `Instance<OidcStep>` | Añadir `@Priority` a las implementaciones si el orden importa; en la implementación actual el orden importa solo en casos de step names solapados (que no deben existir) |
| `OidcFlowContext.toAuthRequest()` debe ser completo | Cubrir con tests unitarios antes de fases 3-4 |
| Ruptura de `formParams` como estado de instancia durante la transición | Pasar `formParams` explícitamente como parte de `StepInput` desde el primer commit — eliminar el campo de instancia en Fase 4 |
| Regresión en flujo de delegated login (más complejo) | Migrar `DelegatedStep` al final (Fase 3, último); tiene tests específicos en el flujo de delegated |

## 7. Resumen ejecutivo

El flujo OIDC actual concentra routing, gestión de cookies, rendering y lógica de
negocio en un `FrontAcessController` de 1121 líneas sin interfaz común entre sus
colaboradores. Añadir un nuevo paso del flujo exige tocar el controlador, la cadena
de dispatch y el mapa de challenges.

La solución introduce cuatro abstracciones:

- **`OidcFlowContext`** — VO inmutable construido una vez por request, elimina la
  propagación manual de parámetros.
- **`StepInput` / `StepOutcome`** — tipado explícito de entrada y salida de cada paso,
  elimina el callback `Function<StepResult, Response>`.
- **`OidcStep`** — interfaz unificada para rendering y procesado, permite registro
  dinámico via CDI.
- **`OidcStepRouter`** — enrutador declarativo que elimina los 13 ifs/cadenas hardcodeadas
  del controlador.

Añadir un nuevo paso del flujo pasará a requerir únicamente:
1. Crear una clase `XxxStep implements OidcStep`.
2. Registrarla como bean CDI.

Sin tocar `FrontAcessController`.
