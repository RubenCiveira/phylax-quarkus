# Contrato A — Código generado integrado con marcas en fichero

El código generado convive con el código manual en los mismos source roots
(`src/main/java` en backend, `src/app` en la SPA), sin separación de directorios.
La frontera se define **fichero a fichero** mediante marcas y se verifica mediante
un manifiesto de hashes.

## Cómo identificar lo generado

Todo fichero generado cumple las tres condiciones:

1. **Anotación estándar** a nivel de clase, reconocida por IDEs y herramientas
   (exclusión de cobertura, inspecciones):

   ```java
   @jakarta.annotation.Generated(value = "net.civeira.phylax.generator.EntityGenerator",
       comments = "model=a3f9c21")  // hash del commit del modelo, nunca fecha (determinismo)
   public class User { ... }
   ```

   En TypeScript, cabecera equivalente:

   ```ts
   /** @generated by phylax-generator — model a3f9c21 — DO NOT EDIT */
   ```

2. **Marca por miembro** `@autogenerated <NombreGenerator>` en el javadoc (ya presente hoy),
   que permite distinguir generadores concretos.

3. **Entrada en el manifiesto** `.phylax/generated-manifest.json` en la raíz de cada repo:

   ```json
   {
     "model": "a3f9c21",
     "generation": 17,
     "files": {
       "src/main/java/net/civeira/phylax/features/access/user/domain/User.java": "sha256:9f2c…",
       "src/main/java/net/civeira/phylax/features/access/user/domain/valueobject/EmailVO.java": "sha256:11ab…"
     }
   }
   ```

El manifiesto es la fuente de verdad operativa: la lista de ficheros que el generador *posee*
(lo que además le permite borrar huérfanos cuando una entidad desaparece del modelo).

## Reglas para el equipo de desarrollo

- **PROHIBIDO** modificar, borrar o renombrar cualquier fichero listado en el manifiesto.
- **PROHIBIDO** crear ficheros nuevos en paquetes cuyo nombre termine en
  `domain/valueobject`, `domain/valueholder` o `usecase/<operación>` (paquetes de propiedad
  exclusiva del generador; lista completa en el manifiesto bajo `ownedPackages`).
- **PERMITIDO** todo lo demás: paquetes nuevos, observadores de los eventos `*Check`/`*Enrich`,
  políticas, controladores de flujos nuevos, componentes Angular propios.
- Para añadir/cambiar campos, entidades u operaciones de maestros: **PR al repo `phylax-model`**.

## Verificación (CI)

En cada PR y en cada push a `main`:

```bash
# 1. El manifiesto es consistente: cada fichero listado existe y su hash coincide
phylax-verify --manifest .phylax/generated-manifest.json   # script committeado, sin dependencias del generador

# 2. Formato canónico
mvn spotless:check
```

Si (1) falla, el PR se rechaza automáticamente con la lista de ficheros alterados.
No hay discusión posible: el hash coincide o no coincide.

## Flujo de regeneración

1. El cliente abre PR en `phylax-model`; el XSD valida en CI; el proveedor lo aprueba.
2. El proveedor, sobre árbol limpio y formato en verde, regenera. La salida ya viene formateada.
3. Commit único de autor `Phylax Generator <gen@civeira.net>` que incluye: ficheros generados,
   manifiesto actualizado y referencia al hash del modelo. Tag `gen/<n>`.
4. El cliente integra ese commit (merge o rebase de sus ramas en curso).
5. CI post-merge: el manifiesto verifica de nuevo. La generación `n` queda como checkpoint para
   diffs y para la próxima regeneración.

## Incumplimientos

- Fichero generado alterado → la regeneración siguiente **lo sobreescribe sin aviso**. El diff
  `gen/<n-1>..HEAD` sobre rutas del manifiesto documenta qué se perdió y en qué commit se introdujo.
- Reincidencia → se renegocia el contrato hacia la variante B o C (frontera física).

## Valoración

| Pros | Contras |
|------|---------|
| Cero cambios en la estructura del proyecto actual | La frontera es invisible al navegar: un dev puede abrir un fichero generado y editarlo sin darse cuenta hasta que el CI le pare |
| Generado y manual del mismo agregado se ven juntos en el IDE | El manifiesto es una pieza más que mantener sincronizada |
| `@Generated` es reconocido por IDEs, JaCoCo, Sonar (exclusiones automáticas) | Paquetes "de propiedad mixta" requieren la lista `ownedPackages`, que es la parte más frágil del contrato |
