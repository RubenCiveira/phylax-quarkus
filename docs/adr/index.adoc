Las decisiones que condicionan el diseño de {project-name} se registran como ADR (_Architecture Decision Records_), un fichero por decisión.

* *Qué se registra*: decisiones significativas (estructura, atributos de calidad, contratos, forma de construir y publicar), con alternativas reales y difíciles de revertir. El _cómo_ se desarrolla en el manual técnico, que enlaza al ADR.
* *Formato*: xref:template.adoc[plantilla] basada en MADR, con el resumen como _Y-statement_ (Zdun y Zimmermann): _en el contexto de…, ante…, decidimos…, y descartamos…, para conseguir…, aceptando…_.
* *Ciclo de vida*: `Propuesta` → `Aceptada` o `Rechazada`. Una decisión aceptada no se edita. Si cambia, se escribe otra que la sustituye, y la anterior pasa a `Sustituida`, o a `Obsoleta` si simplemente deja de aplicarse.
* *Ámbito*: `común` para lo que comparte toda aplicación (`bootstrap`, `common`, `features`), o el módulo opcional al que pertenece. Las de un módulo solo aparecen si el módulo está declarado en `site-attrs.adoc`.
* *Numeración*: correlativa y nunca reutilizada. Una decisión de módulo conserva su número aunque el módulo no esté presente.

== Candidatas pendientes de registrar

Decisiones que ya están tomadas en el código, pero sin ADR:

* Generación de código a partir de un modelo, con _Generation Gap_ (marca `@autogenerated`).
* Quarkus con imagen nativa como despliegue de referencia.
* JDBC directo, sin ORM.
* Datasource de lectura en réplica, con ventana de escrituras pendientes.
* Paginación por cursor (keyset).
* Eventos CDI como punto de extensión de los casos de uso, entregados de forma síncrona dentro de la transacción (pendiente de revisar).
* Huellas HMAC con _pepper_ para los secretos que solo se comparan, y cifrado AES-GCM con anillo de claves para los que hay que recuperar.
* RBAC con almacenes intercambiables y decisión por defecto configurable.
* Logs JSON estructurados y trazas OpenTelemetry.
