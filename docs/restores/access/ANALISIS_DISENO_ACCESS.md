# Análisis de diseño de `features/access`

> Fecha: 2026-10-20 · Rama `feat/refactor-oidc` · Alcance: `src/main/java/net/civeira/phylax/features/access` y el código de `common` del que depende (seguridad, paginación, caché).
> Método: análisis estático del código y de las migraciones. Se ha tomado como base el análisis anterior, [docs/analisis-diseno-clases.md](../../../docs/analisis-diseno-clases.md) (2026-06-11), comprobando qué sigue vigente (§2). No se han ejecutado tests ni la aplicación: los hallazgos marcados como *probables* necesitan un test que los confirme.

## 1. Resumen

`access` reúne **21 agregados y 1.788 ficheros**, generados en su totalidad. Los 98 ficheros sin la marca `@autogenerated` son clases de evento, también generadas. La estructura hexagonal es **coherente y predecible**:

- el dominio no depende de ningún framework;
- la aplicación no depende de la infraestructura;
- los puertos de lectura, escritura, caché y auditoría están separados;
- todos los casos de uso siguen el mismo pipeline.

A nivel de diseño, **la estructura es buena**. Los problemas están en **lo que las plantillas generan por defecto**, sobre todo en autorización, y en algunas piezas comunes (paginación, caché, contraseñas).

| Aspecto | Valoración | En una frase |
|---|---|---|
| Estructura y capas | **Buena** | Anatomía idéntica en todos los agregados; dirección de dependencias correcta |
| Modelo de dominio | Aceptable | Entidades inmutables con transiciones y eventos; dominio anémico y VO que solo validan el tipo |
| Autorización | **Crítica** | *Fail-open*: el permiso parte de `allow`, el RBAC está desactivado por defecto, no hay autenticación HTTP obligatoria y 10 de los 13 maestros con API no tienen ninguna política de autorización |
| Persistencia y paginación | Insuficiente | El orden descendente está roto en 8 DAO y el `Slider` pagina mal al ordenar |
| Integración con `oauth` | Insuficiente | `oauth` escribe directamente en los repositorios y se salta la auditoría, la caché y las políticas |
| Seguridad de credenciales | **Crítica** | Las contraseñas de usuario se guardan **cifradas de forma reversible**, no como hash |
| Tests | Insuficiente | 429 tests generados; ninguno prueba denegaciones de acceso, paginación real ni SQL |

**Prioridad inmediata:** §4.1–§4.3 (autorización, actor anónimo y contraseñas).

## 3. Estructura

### 3.1 Dos tipos de agregado

| Tipo | Agregados | Capas |
|---|---|---|
| **Maestro con API** (13) | `apikeyclient`, `consentpurpose`, `relyingparty`, `role`, `tenant`, `tenantconfig`, `tenantloginprovider`, `tenanttermsofuse`, `trustedclient`, `user`, `usergroupmembership`, `userpersonalapikey`, `userroleassignment` | `domain` + `application` (casos de uso, `policy`, `visibility`, `importation`) + `infrastructure` (REST, JDBC, caché, auditoría, RBAC) |
| **Agregado interno** (8) | `useracceptedtermsofuse`, `useraccesstemporalcode`, `userconsentedscopes`, `userconsentpurposes`, `userinvitation`, `usermfarecoverycode`, `userprofile`, `userwebauthncredential` | Solo `domain` + `infrastructure/repository` y `driven`. Sin casos de uso ni API: solo los usa `oauth` (§4.5) |

Anatomía de un maestro (`role`, 81 ficheros y 8.885 líneas para 4 atributos):

```
domain/          Role (inmutable, @With, eventos), RoleChangeSet, RoleRef/RoleReference,
                 valueobject/*VO, valueholder/*ValueHolder, event/*, gateway/* (Query, Command, Cache, Audit, Filter, Cursor, Order)
application/     usecase/{create,retrieve,list,update,delete}/  Usecase + Input + Projection + Check + Enrich + AuthorizationDecision
                 visibility/  RolesVisibility + 7 eventos de extensión
                 policy/      listeners CDI (no existe en role)
                 importation/
infrastructure/  driver/rest (fachada que implementa la interfaz OpenAPI + un controller por operación)
                 driven (adaptadores de los gateways), repository (JdbcDao + Slider), event, bootstrap (RBAC, proyecciones)
```

### 3.2 Fortalezas (mantener)

- **Regla de dependencia limpia:** `*/domain` no importa `jakarta`, `io.quarkus`, `opentelemetry` ni `java.sql`, ni tampoco `application` o `infrastructure`. `application` no importa `infrastructure`.
- **Pipeline uniforme** ([RoleCreateUsecase.java](../../main/java/net/civeira/phylax/features/access/role/application/usecase/create/RoleCreateUsecase.java)): permiso → campos fijos → `Check` → `Enrich` → dominio → persistencia con verificación de visibilidad → caché → auditoría → proyección sin campos ocultos. Las políticas se añaden como observers CDI sin tocar el caso de uso (OCP).
- **Lecturas réplica/primario con `PendingWritesRegistry`:** tras una escritura, las lecturas van al primario durante una ventana configurable. Es una solución elegante a la consistencia eventual de la réplica.
- **Bloqueo optimista** con `version` en el `WHERE` de los `UPDATE`.
- **Esquema con integridad:** las FK de todas las referencias y los índices únicos de negocio (`UK_USER_TENANT_NAME`, `UK_ROLE_RELYING_PARTY_NAME`, `UK_CONSENT_PURPOSE_TENANT_TITLE`…) están en las migraciones.
- **Referencias entre agregados por `XxxRef`/`XxxReference`**, no por entidades anidadas.

### 3.3 Grafo de dependencias entre agregados

```
role ↔ relyingparty          tenant ↔ user              (solo a través de *ProjectionDescriptor)
userroleassignment → user, role, trustedclient, relyingparty
usergroupmembership → user, trustedclient, relyingparty
tenant → consentpurpose, tenantconfig, tenantloginprovider, tenanttermsofuse, user
```

Los ciclos (`tenant ↔ user`, `relyingparty ↔ role`…) solo aparecen en `infrastructure/bootstrap/*ProjectionDescriptor`, es decir, en el wiring de proyecciones. No afectan a dominio ni a aplicación, pero convendría mover esos descriptores a `bootstrap/` (composition root), como ya proponía el análisis anterior, y fijar las reglas con ArchUnit.

## 4. Hallazgos

### 4.1 Crítico — Autorización *fail-open* por diseño

Hay cuatro piezas, y cada una por separado es razonable. Juntas dejan los maestros abiertos:

1. **Cada caso de uso parte de `allow`:** `Permission.allow("Allow to create by default")` ([RoleCreateUsecase.java:122](../../main/java/net/civeira/phylax/features/access/role/application/usecase/create/RoleCreateUsecase.java#L122)). Los observers solo pueden denegar.
2. **El RBAC está apagado y permite por defecto:** `mp.rbac.model` está comentado en [security.yaml](../../main/resources/config/security.yaml), así que no hay `RbacStore` activo, y `app.security.rbac.default-allow: true` hace que `Rbac.checkAllow` devuelva `allow` ([Rbac.java:106](../../main/java/net/civeira/phylax/common/security/Rbac.java#L106)).
3. **No hay autenticación obligatoria en HTTP:** ni `@Authenticated` / `@RolesAllowed` ni `quarkus.http.auth.permission.*`. Las interfaces OpenAPI generadas (`/api/access/...`) no llevan anotaciones de seguridad.
4. **Las políticas existen solo para algunos maestros** (tabla siguiente). Las más habituales (`TenantAccessible`, `FixTenantExcludingRoot`, `InheritTenantExcludingRoot`) filtran la **visibilidad** y fijan el **tenant**, pero no deciden **quién** puede operar.

| Maestro | Política de autorización (`*AuthorizationDecision`) | Visibilidad / tenant | Consecuencia con la configuración por defecto |
|---|---|---|---|
| `apikeyclient`, `relyingparty`, `trustedclient` | `OnlyForRoot` en todas las operaciones | — | ✅ Solo un administrador root |
| `tenant` | `OnlyForRoot` en las escrituras | `TenantAccessible` | ✅ |
| `userpersonalapikey` | `IsSelfUser` en retrieve, update, delete y revoke | `OnlySelfAccessibles`, `InheritUser` | ✅ Solo el propietario |
| `user`, `consentpurpose`, `tenantconfig`, `tenantloginprovider`, `tenanttermsofuse` | **Ninguna** | Tenant del actor | ⚠️ **Cualquier usuario autenticado** puede crear, modificar y borrar usuarios, configuración, proveedores de login y términos **de su tenant** |
| `userroleassignment`, `usergroupmembership` | **Ninguna** | Tenant del actor | ❌ **Escalada de privilegios:** cualquier usuario del tenant puede asignarse roles o grupos a sí mismo |
| `role` | **Ninguna** | **Ninguna** (no tiene tenant) | ❌ Cualquiera puede gestionar los roles de **todas** las relying parties |

Si `mp.rbac.model` se activa, `RbacAuthorizationDecisionListener` sí exige el permiso `resource:action` para cada operación, así que el diseño es correcto **siempre que el RBAC esté encendido**. El problema es que el sistema, tal como se distribuye, **deja todo permitido** y nada lo detecta.

**Recomendación:**

- `default-allow: false` por defecto, y arrancar con error si no hay un `RbacStore` activo fuera de `dev`.
- Exigir autenticación en `/api/*` (`quarkus.http.auth.permission`), salvo en las rutas públicas declaradas.
- En el generador: que el permiso inicial sea `deny` cuando el modelo no declara ninguna política, o que el modelo obligue a declarar una por operación.
- Añadir `OnlyForRoot` o un equivalente por rol de tenant (`tenant-admin`) a `role`, `userroleassignment`, `usergroupmembership`, `user`, `tenantconfig` y `tenantloginprovider`.
- Tests de denegación para cada maestro (anónimo, usuario normal, admin de otro tenant).

### 4.2 Crítico — El actor anónimo desactiva el filtro de tenant

En [CurrentRequest.java:213](../../main/java/net/civeira/phylax/common/infrastructure/CurrentRequest.java#L213), un actor anónimo se construye **sin tenant ni scopes**. Las políticas de visibilidad hacen:

```java
if (!actor.hasScope("platform:global_access")) {
  filter.peek(fl -> fl.setTenantAccessible(actor.getTenant()));   // getTenant() == null
}
```

([user/…/TenantAccessible.java:16](../../main/java/net/civeira/phylax/features/access/user/application/policy/TenantAccessible.java#L16)). `getTenantAccessible()` devuelve `Optional.ofNullable(null)`, que es vacío, y el DAO **no añade el `WHERE tenant = ?`**. El anónimo, que debería ser el actor más restringido, termina viendo **todos los tenants**. En escritura, `InheritTenantExcludingRoot` asigna `TenantReference.of(null)`.

Junto con §4.1, y salvo que haya un gateway externo que exija autenticación, `GET /api/access/users` sin token **devolvería los usuarios de todos los tenants**. Es *probable*; hay que confirmarlo con un test de integración.

**Recomendación:** en las políticas generadas, si el actor no está autenticado o no tiene tenant, **denegar** (o aplicar un filtro imposible) en lugar de no filtrar. Mejor todavía, que el filtro de visibilidad no admita «sin valor» como «sin restricción».

Otros defectos en `getActor()`:

- [CurrentRequest.java:255](../../main/java/net/civeira/phylax/common/infrastructure/CurrentRequest.java#L255) hace `claims.put(string, claim.toString())` usando la variable `claim` del `tid` en vez de `claimWithName`: lanza NPE cuando no hay `tid`, y el mapa resultante no se usa.
- Sin `tid`, el tenant del actor pasa a ser el **issuer** (una URL) ([línea 249](../../main/java/net/civeira/phylax/common/infrastructure/CurrentRequest.java#L249)), que no coincide con ningún uid de tenant.
- `uid` = `sub` del JWT, que en los tokens de `oauth` es el *username*; el uid real va en el claim `uid`.

### 4.3 Crítico — Contraseñas de usuario cifradas de forma reversible

[PasswordVO.java:102-115](../../main/java/net/civeira/phylax/features/access/user/domain/valueobject/PasswordVO.java#L102-L115) guarda la contraseña con `AesCipherService.encryptForAll` (una clave global) y el login la **descifra y compara con `equals`** ([UserLoginService.java:250](../../main/java/net/civeira/phylax/features/oauth/user/infrastructure/UserLoginService.java#L250)). Quien tenga la base de datos y la clave de cifrado (`security.encriptation.key`, con valor por defecto `eventual`) obtiene **todas las contraseñas en claro**. La comparación, además, no es de tiempo constante.

El análisis anterior lo trató como un problema de dependencias (§3.4, dominio → clase CDI). Es, ante todo, un problema de seguridad.

**Recomendación:** hash adaptativo (Argon2id o bcrypt) detrás de un puerto `PasswordHasher` en `common/security`. `PasswordVO` guarda solo el hash y expone `matches(raw, hasher)`. Hace falta una migración que rehashee en el siguiente login correcto. La semilla MFA (TOTP) sí tiene que ser reversible y puede seguir cifrada. Aparte, `checkPassword` **se salta la comprobación cuando `password == null`**: hoy ninguna ruta llega con `null`, pero es una trampa latente.

### 4.4 Alto — Paginación por cursor rota al ordenar

Son tres defectos de plantilla, replicados en todos los agregados:

| Defecto | Evidencia | Efecto |
|---|---|---|
| El orden descendente usa `>` | [RoleJdbcDao.java:613](../../main/java/net/civeira/phylax/features/access/role/infrastructure/repository/RoleJdbcDao.java#L613) (`tryToOrderByNameDesc` con `SqlOperator.GT`); igual en **los 8 DAO** que tienen orden descendente | La página siguiente en `NAME_DESC` devuelve las filas **anteriores** o ninguna |
| El `Slider` solo avanza `sinceUid` | [RoleSlider.java:54-55](../../main/java/net/civeira/phylax/features/access/role/infrastructure/repository/RoleSlider.java#L54-L55): `cursor.withSinceUid(last.getUid())` conserva el `sinceName` original | Al ordenar por nombre, la consulta de relleno filtra por `uid > X` en lugar de `(name, uid) > (N, X)`: **es probable que se dupliquen filas** en la última página (21 sliders) |
| El `Slider` pagina desde el último elemento **aceptado** | [Slider.java:127-131](../../main/java/net/civeira/phylax/common/algorithms/Slider.java#L127-L131) pasa `filteredData` a `next(...)` | **Latente.** Hoy el predicado siempre acepta, porque no hay políticas `*AccessibleCheck`. Cuando se añada una: si el primer lote no tiene ningún visible, `roles.get(-1)` lanza `IndexOutOfBoundsException`; si la cola de un lote se descarta entera, se repite la misma consulta indefinidamente |

**Recomendación (plantilla):**

- Operador `LT` en descendente.
- `next(...)` recibe el último elemento **leído**, no el último aceptado, y actualiza todas las columnas del cursor.
- Test de contrato del generador: dos páginas consecutivas con nombres repetidos, en orden ascendente y descendente, con filtros que excluyen filas.

### 4.5 Alto — `oauth` se salta la capa de aplicación de `access`

`oauth` usa directamente los `*CommandRepositoryGateway` de `user` (7 ficheros), `useraccesstemporalcode`, `userconsentedscopes`, `useracceptedtermsofuse`, `userprofile`, `userwebauthncredential`, `usermfarecoverycode`, `userinvitation` y `tenantconfig`. Así ocurre lo siguiente:

- **No hay auditoría** (`*AuditGateway` solo lo llaman los casos de uso) de cambios sensibles: contraseña, bloqueo, semilla MFA, passkeys, códigos de recuperación.
- **La caché no se actualiza:** el adaptador marca *pending writes*, pero `cache.update` solo se llama desde los casos de uso, así que las listas cacheadas de `user` pueden servir datos viejos durante 10 minutos (§4.6).
- No se aplican políticas ni `Check`/`Enrich`. Eso es aceptable para operaciones del propio sistema, pero tiene que ser una decisión explícita.

Los 8 agregados internos no tienen capa de aplicación, así que cualquier regla sobre ellos acaba viviendo en `oauth`.

**Recomendación:** decidir el contrato. Hay dos opciones:

- **(a)** Generar para los agregados internos casos de uso «de sistema» (sin API REST) que incluyan auditoría y caché, y que `oauth` los use.
- **(b)** Mover la auditoría y la invalidación de caché al `CommandRepositoryAdapter`, para que se apliquen se escriba desde donde se escriba.

La (b) es más barata y cubre también los batch.

### 4.6 Medio — Caché local con lecturas desactualizadas

- Es Caffeine en memoria (10 min, 100 entradas; [cache.yaml](../../main/resources/config/cache.yaml)). Con más de una instancia, la invalidación de un nodo no llega al resto.
- `RoleCacheAdapter.retrieve` no consulta `pendingWrites` (solo `store` lo hace), así que tras una escritura que no pase por el caso de uso (§4.5) se siguen sirviendo entradas antiguas.
- `cache.get(key, _ -> null)` ([RoleCacheAdapter.java:68](../../main/java/net/civeira/phylax/features/access/role/infrastructure/driven/RoleCacheAdapter.java#L68)) puede guardar el *miss* como valor.

**Recomendación:** invalidar en `retrieve` mientras haya *pending writes*, usar `getIfPresent` y, si se despliega con más de una réplica, usar caché distribuida o desactivar la caché de listas.

### 4.7 Medio — Eventos de dominio síncronos y sin consumidores

- `RoleEventDispatcher` lanza los eventos con `Event.fire` **dentro de la transacción** y antes del commit. El controller REST abre la transacción (`@Transactional` en [RoleCreateController.java:35](../../main/java/net/civeira/phylax/features/access/role/infrastructure/driver/rest/RoleCreateController.java#L35)), el caso de uso no.
- Los únicos consumidores, `NotifyCreate` y `NotifyRecover` en `oauth`, **están vacíos**.
- El módulo `notification` sí usa `TransactionPhase.AFTER_SUCCESS` y un outbox: es el patrón al que conviene converger.

**Recomendación:** documentar que los eventos de `access` son internos y síncronos, o publicarlos `AFTER_SUCCESS` / por outbox. Borrar los listeners vacíos o implementarlos. Considerar mover `@Transactional` al caso de uso, para que los usos no REST (batch, importación, `oauth`) tengan los mismos límites transaccionales.

### 4.8 Medio — Modelo de dominio anémico y VO sin reglas

- `NameVO.tryFrom` solo comprueba `null` y el tipo: acepta `""` y cadenas de cualquier longitud (la columna es `VARCHAR(255)` y el error llega desde la base de datos). Se mantiene la crítica de §3.2–3.3 del análisis anterior.
- `Role` expone `@Builder` y `@With` públicos: se puede construir o modificar una instancia **sin pasar por el constructor que acumula `ConstraintFailList` y sin registrar eventos**. Las fábricas `create`/`update` son el camino previsto, pero nada lo obliga.
- No hay observers de `*Check` en ningún agregado: las reglas de negocio (p. ej. «no borrar un rol asignado», «no borrar una relying party con roles») no existen y se delegan en las FK. Una violación de FK no se traduce a un error de dominio, porque `UncheckedSqlException` solo mapea duplicados, y acaba en 500.

**Recomendación (generador):**

- Reglas de validación declaradas en el modelo (longitud, formato, `not-blank`) y ejecutadas en `tryFrom`, usando los validadores de `common`.
- `@Builder` / `@With` con acceso de paquete o restringido a infraestructura.
- Mapear la violación de FK a una `ConstraintException` (409).

### 4.9 Bajo — Detalles de las plantillas

- `RoleRbacRegister`: todas las acciones tienen `description("list")` ([RoleRbacRegister.java:37-39](../../main/java/net/civeira/phylax/features/access/role/infrastructure/bootstrap/RoleRbacRegister.java#L37-L39)), y el campo `name` de `role` se describe como «The user name to identify on the login screen» (copiado de `user`). Esas descripciones se publican en el RBAC externo.
- Los 32 `*InBatchExecutor` mantienen el bloque de spans manual (análisis anterior, §3.4).
- `RoleCreateInput` acepta `uid` y `version` del cliente: el cliente elige el identificador y la versión inicial. Conviene ignorar `version` al crear.
- Las clases de `policy` no tienen anotación de scope CDI y funcionan porque ArC trata como bean cualquier clase con un `@Observes`. Es mejor declarar `@ApplicationScoped` explícitamente: si una política deja de cargarse, no salta ningún error.
