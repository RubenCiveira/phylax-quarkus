= Generación de código

Gran parte del código y de la documentación se genera con `civi-generator` a partir de un modelo XML (en {project-name}, `multitenant-oidc.xml`). El modelo describe las entidades, sus campos, relaciones, casos de uso y políticas.

== Qué se genera

* Las entidades de `features` declaradas en el modelo (en {project-name}, `features/access` completo): entidades, casos de uso, controladores, adaptadores y eventos.
ifdef::module-oauth[]
* Parte de `features/oauth`, a partir de las plantillas Quarkus del generador.
endif::[]
* La migración de esquema (`src/main/resources/migration/mysql`).
* La documentación de las entidades (`docs/technical/contexts/<contexto>/entities`) y los diagramas C4.

== Generation Gap

Cada fichero o bloque generado lleva la marca `@autogenerated`: en Java, en el Javadoc o en la cabecera (`/* @autogenerated */`); en AsciiDoc, `// @autogenerated`. Las reglas son:

* Lo que lleva la marca se sobrescribe en cada regeneración. *No se edita a mano.*
* Un fichero generado como punto de partida pasa a ser del desarrollador cuando se le quita la marca. A partir de ese momento el generador no lo toca.
* La lógica propia no se escribe dentro del código generado. Se escribe en observadores (`application/policy`) de los eventos `AuthorizationDecision`, `Check` y `Enrich`.

== Flujo de un cambio

. Un cambio de esquema (campo, entidad, relación) se hace en el modelo, nunca en las clases generadas ni en la migración.
. Se regenera y se revisa el diff.
ifdef::module-oauth[]
. Los cambios a mano en `features/oauth` se llevan antes a la plantilla con `.make/binary/sync-oidc-template.py --apply` (`--include-new` para clases nuevas). Si no, la regeneración los pierde. `--check` comprueba que no queden diferencias.
. El mismo modelo alimenta la plantilla PHP (`lughauth-api`): los renombrados se trasladan también allí.
endif::[]

Muchas correcciones pendientes (ver link:{docs-root}/plan/TODO/README.md[backlog de diseño]) se hacen en el generador, no en este repositorio.
