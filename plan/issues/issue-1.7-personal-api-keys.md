# Issue 1.7 — Personal API Keys — REST driver and M2M authentication

**Model section:** 1.7  
**OAUTH_PLAN:** PLAN-26 (Personal Access Tokens for Users)  
**Wave:** 4

## Current state

- `access_user_personal_api_key` table exists in DB ✅.
- Domain: `UserPersonalApiKey` entity with `uid`, `user`, `name`, `keyHash`, `scopes`,
  `lastUsedAt`, `expiresAt`, `createdAt`, `enabled` ✅.
- Application use cases: `create`, `delete`, `list`, `retrieve`, `update` exist ✅
  (generated by model compiler).
- Infrastructure: read/write adapters and repository exist ✅.
- **No REST driver** for the self-service key management endpoints.
- **No authentication path** that accepts API keys as bearer credentials.

## What to implement

### 1. REST driver — self-service key management

`features/access/userpersonalapikey/infrastructure/driver/rest/UserPersonalApiKeyController.java`

Endpoints (scoped to the authenticated user, not admin):

```
GET    /access/{tenant}/me/api-keys           — list own keys (name, scopes, lastUsedAt, expiresAt; never keyHash)
POST   /access/{tenant}/me/api-keys           — create key → returns raw key ONCE
DELETE /access/{tenant}/me/api-keys/{uid}     — revoke (hard delete) or disable
```

**Key creation flow:**
1. Generate cryptographically random raw key (32 bytes, Base64URL — reuse `SecureTokenService`
   from PLAN-18 when available, or implement inline with `SecureRandom`).
2. Compute `SHA-256` hex digest → `keyHash`.
3. Call `UserPersonalApiKeyCreateUsecase` with `keyHash`, `name`, `scopes`, optional `expiresAt`.
4. Return the raw key in the response body — **this is the only time it is returned**.

The controller must authenticate via the session cookie or a bearer token (not via API key,
to avoid a bootstrapping loop).

### 2. API Key authentication adapter

`features/oauth/authentication/infrastructure/driven/ApiKeyAuthAdapter.java` (or similar)

Implement an authentication path that accepts `Authorization: Bearer {rawKey}`:
1. Compute `SHA-256` of the raw bearer value.
2. Query `UserPersonalApiKeyReadRepositoryGateway` by `keyHash`.
3. Reject if: not found, `enabled=false`, or `expiresAt < now()`.
4. Call `UserPersonalApiKeyWriteRepositoryGateway` to update `lastUsedAt = now()` (async or
   best-effort — do not fail the request if the touch fails).
5. Load the associated user and return an `AuthenticationData` with `userId`, `scopes` from
   the key, and `acr=1` (password-equivalent — no MFA for API keys).

This adapter is called from whichever `AuthenticationFilter` or `ContainerRequestFilter` handles
bearer tokens before the regular JWT verification path.

### 3. Scope intersection

When issuing a token for an API-key-authenticated request, the granted scopes must be the
**intersection** of the key's `scopes` and the client's `allowedScopes`. Never grant more scopes
than the key declares.

### 4. Discovery / discovery document

API keys are not an OIDC grant type — do not add them to `grant_types_supported`. They are
an authentication method for direct API access, not for the authorization code flow.

## Notes

- PLAN-18 (`SecureTokenService`) provides the shared hashing helper. If this issue is implemented
  before PLAN-18, use `MessageDigest.getInstance("SHA-256")` inline and refactor later.
- The `revoke` action generates a `UserPersonalApiKeyUpdateEvent` (sets `enabled=false`).
  Hard delete (DELETE endpoint) generates `UserPersonalApiKeyDeleteEvent`. Both are acceptable;
  choose based on whether the audit trail needs soft-delete semantics.
